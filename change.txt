2. WHAT App.tsx WAS
--------------------------------------------------------------------------------

A single App() component containing:
  - ~55 useState hooks
  - ~15 useEffect hooks
  - ~25 async chain/contract functions
  - 12 render* closures (renderCommunityFeed alone was ~390 lines)

Everything shared one closure, which is why it could not be split
mechanically - the render functions read dozens of local variables directly.

** IMPORT ORDER IS LOAD-BEARING **

The original file redefined some selectors later to deliberately override
earlier ones:
    .post-card    line  465, again at 1363 (gains position:relative so the
                  kebab can be pinned to it)
    .comment-item lines 597, 1306, 1379 (gains right padding so text clears
                  its kebab)

Because of this, the split cuts CONTIGUOUS line ranges only and re-imports
them in the original order. Do not sort or regroup the @import list. Put new
rules in the file matching their concern; only use overrides.css when you
specifically need to beat an earlier rule.

5. HOW THE STATE LAYER IS ORGANISED (important for future edits)
--------------------------------------------------------------------------------

Dependency rule: domain hooks depend on `core` (translate, contracts, status)
and on loaders passed into them. Loaders never call actions; actions call
loaders. The hook call order in useForumState.ts is a topological sort of that
graph - each hook only receives loaders from hooks constructed above it.

One cycle existed and was removed rather than worked around:
    moderation needed loadPosts/loadCommunities
    posts/communities needed loadModeratorInfo

Fixed by splitting moderation into:
    useModeratorRoster.ts    - read side, depends on nothing (constructed early)
    useModerationActions.ts  - write side, takes loaders (constructed late)

An earlier attempt wired this with refs instead; lint correctly rejected it
(variable accessed before declaration, ref mutation during render). Merging
those two hooks back together would reintroduce the cycle.

6. BEHAVIOUR CHANGES (the only intentional ones)
--------------------------------------------------------------------------------

Four setState-in-effect issues were found and fixed. These were NOT introduced
by the refactor - they existed in the original App.tsx.

Verified: linting the original App.tsx from git shows it contains
`setFeedPage(1)` inside a useEffect at line 427, yet the rule reported ZERO
violations. The React Compiler-based analyzer was silently bailing out on the
3921-line component. Splitting the file is what made them visible.

Each caused a cascading render (render stale value, then immediately re-render):

  a) useFeedPagination - page clamp when the list shrinks
  b) useFeedPagination - reset to page 1 on community/page-size change
  c) useUsernameDirectory - clearing availability when the input empties
  d) useForumState - collapsing the expanded post on community change

Fixes (a,b,d) adjust state during render, React's documented pattern.
Fix (c) derives the value instead of storing and clearing it.

FLOWS TO SMOKE-TEST because of the above:
  [ ] feed pagination: page numbers, page-size chips, shrinking list
  [ ] username availability text while typing / clearing the field
  [ ] expanding a post, then switching community (selection should clear)

One bug I introduced during the refactor and caught on review:
  ProfileView originally consulted usernamesCache[profileAddress] before
  profileData?.username. My first version dropped that, which would have shown
  the wrong display name for cached users. Fixed; usernamesCache is exposed on
  the context.
